# 决策：tool_execution_start 的 await 语义是设计基础

状态：已实施
类别：architecture

## 背景

编辑前备份必须在工具实际写盘**之前**完成，否则备份记录的是编辑后内容，恢复时静默错误。pi 的 `tool_execution_start` 扩展事件是 **await emit**（源码 `agent-session.js` 中工具执行等待 handler 返回）。

## 决策

直接依赖 pi 的 await 语义：handler 保持 `async` + `await engine.trackEdit(abs)`，保证备份先于编辑完成、无竞态。**禁止改成 fire-and-forget**（`void (async()=>{})()`）——那会牺牲顺序保证换毫秒级「不阻塞」，大文件下必竞态。

## 已考虑替代方案

- **fire-and-forget（后端并行备份）**：`void (async()=>{ await trackEdit... })()` 立即返回，工具不等。曾短暂实现又回滚（二轮审查 + 实现者「优化」）。落选根因：备份的 stat+copyFile 与工具写盘竞态；且 spec 从一开始就依赖 await 语义——这是回归不是改进。
- **在 message_end 统一备份下一轮**：语义错位（下一轮开始才备份，丢失本轮编辑前状态）。落选。

## 后果

- 每次 edit/write 前有一次同步备份 IO 延迟（stat + 通常毫秒级 copyFile）。因工具执行本身也 async IO，可接受。
- 代价是可预期的顺序正确性；为「优化」它付出的竞态风险已被证明不值得（见 [EXPERIENCE#4](../EXPERIENCE.md#4-tool_execution_start-是-await-语义是特性不是负担)）。
